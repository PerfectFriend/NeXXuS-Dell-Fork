# Процесс циклического аудита NeXXuS-Dell-Fork

Цель: довести текущую кодовую базу до «конфетки» до начала новой разработки
(ADR-0011 multi-transport и далее). Цикл: **аудит → план → исполнение → повторный аудит**.

## Как складываются отчёты

Владелец прогоняет весь репозиторий через три внешние модели
(Grok, Gemini 4 Argon, Claude Sonnet 5.5) и кладёт сырые отчёты сюда:

```
AUDIT/reports/<дата>-<модель>.md      # сырой отчёт модели, как есть
```

Каждый отчёт должен отвечать на вопросы (шаблон — `AUDIT/REPORT_TEMPLATE.md`):

1. Что проверено (область: безопасность / wire-протокол / сеть / хранилище /
   crypto / экономику / deploy / UI / документация / тесты).
2. Найденные дефекты: для каждого — **severity (S1..S4), файл:строки, описание,
   точная рекомендация по исправлению, пример исправленного кода если применимо**.
3. Что проверено и признано годным (чтобы не перемалывать дважды).
4. Рекомендуемый порядок исправлений.

## Что делаю я (Hermes) на каждом цикле

1. Читаю все отчёты в `AUDIT/reports/` + baseline-проверки
   (`scripts/check-tree-hygiene.sh`, `cargo clippy --workspace --all-targets`,
   `cargo test --workspace`, ручной smoke на живом хосте).
2. Дедуплицирую и приоритизирую → пишу `AUDIT/PLAN-<дата>.md`
   (единый план эволюции: задачи, файлы, критерии «сделано», порядок).
3. Исполняю план коммитами в `main` (каждая задача — отдельный коммит, зелёные тесты).
4. После исполнения — baseline снова + запись в `AUDIT/CYCLES.md`, новый цикл.

## Severity

- **S1** — уязвимость / утечка секретов / потеря данных / падение ноды. Правим сразу.
- **S2** — некорректное поведение протокола/хранилища под нагрузкой, race, таймауты.
- **S3** — некорректная обработка ошибок, schlecht UX, дребезг логов.
- **S4** — косметика, документация, именование.

## Правила

- Аудит идёт по **отслеживаемым файлам** (то, что в git), без `target/`,
  `node_modules/`, `dist/`.
- Секреты (мнемоники, токены) в отчётах запрещены — только факт утечки и где.
- Каждый цикл заканчивается тегом `audit-cycle-N` в форке.
