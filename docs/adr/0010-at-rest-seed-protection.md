# ADR-0010 (ЧЕРНОВИК для решения владельца): at-rest шифрование не защищает от кражи файла стора

**Статус:** Предложен, 2026-11-18. Ничего не реализовано — ожидается выбор варианта (S4 письма кодеру).
**Находка:** `at_rest.rs` выводит ключ стора из seed через HKDF-SHA256 (`StoreKey::derive(seed)`), а `identity_store.rs` кладёт сам seed (BIP-39 мнемонику) открытым текстом в таблицу `meta` того же `store.redb` (`META_IDENTITY_MNEMONIC`, 5 точек записи/чтения). Бэкапы и копия на внешний носитель getragenся вместе со стором и содержат мнемонику. `THREAT_MODEL.md` §3–4 и пункт D2 утверждают обратное.

## Вариант (а) — убрать plaintext-seed из `meta`, seed жить только в зашифрованном vault

Уже есть `seed_vault.rs`: AES-256-GCM vault с PBKDF2-600k, файл `<store>.seed.vault` рядом со стором, atomic tmp+rename, mode 0600. Вариант: `identity_mnemonic` из `meta` **не пишем**; при старте seed либо разблокируется из vault по PIN, либо берётся из systemd-credential (`LoadCredential=`), расшифровывается в память (Zeroizing) и хранилище открывается.

Миграция двухфазная (по STR-02):
1. Фаза 1: при старте, если в `meta` есть мнемоника, а vault нет — создаём vault из неё (PIN запрашиваем один раз), `meta` пока не трогаем. Нода работает как раньше.
2. Фаза 2: после успешного старта с vault (и N чистых рестартов / ручного подтверждения) — удаляем `identity_mnemonic` из `meta`. До удаления бэкапы содержат и то, и другое.

**Объём:** `identity_store.rs` (~5 точек `put/get_meta`), `main.rs` (unlock-flow: vault→PIN или systemd-credential→decrypt), миграционный код + тесты (создать стор со старой схемой → старт → vault появился, meta удалена после фазы 2; rollback). Оценка: **2–3 дня** код+тесты. Риски: забытый PIN = потеря доступа к ноде (нужен documented recovery через 12 слов, которые пользователь хранит отдельно); systemd-credential работает только на systemd-хостах — нужен фолбэк на PIN.

## Вариант (б) — честно переписать модель угроз

Оставляем код как есть, но `THREAT_MODEL.md` §3–4, пункт D2 и формулировки в `audit-package` переписываем: «at-rest шифрование защищает payload чанков от случайного чтения файла, но не от владельца файла / того, кто имеет и store.redb, и бэкапы — мнемоника в нём в открытом виде». Убираем любые утверждения про «защиту на внешнем носителе» и пометки «Secure at rest» из README/презентаций.

**Объём:** только документы — **0.5 дня**. Риски: внешний аудитор читает «шифрование не защищает от кражи файла» как слабую позицию; маркетинговое «at-rest encryption» снимается.

## Сравнение

| | (а) vault-only | (б) честный THREAT_MODEL |
|---|---|---|
| Убирает ли реальную уязвимость (кража файла = потеря идентичности) | Да | Нет (декларируем) |
| Объём | 2–3 дня + миграция | 0.5 дня, документы |
| Риск регрессии | Средний (миграция, PIN-flow) | Нет |
| Восприятие аудиторами | Сильное | Слабое, если есть претензия «Secure» |
| Совместимость со старыми сторами | Через двухфазную миграцию | Полная |

## Рекомендация

Вариант (а): `seed_vault` уже реализован, так что по сути убирается **дублирующая** plaintext-запись в `meta`; двухфазная миграция снижает риск. Если сроки давят — сначала (б) на один релиз (убрать ложные утверждения), потом (а).
